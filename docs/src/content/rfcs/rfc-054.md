## Context

A jurist who checks a translation reads the law and the YAML side by side. The
YAML is written for the engine, not for that reader, so every tool that shows
an action to a person invents its own reading of the tree. There are two
today, and neither reads a whole rule:

- **The editor** (`frontend/src/utils/operationTree.js`) labels each node with
  `OPERATION_LABELS` and a one-line `describeSubtitle`. It is a summary by
  design: past three operands it says "5 condities", it picks the first
  variable inside a nested operation as its name, and it shows `ROUND`, `CEIL`
  and `FLOOR` as their codes because they have no label.
- **The presenter** (`frontend-presenter`, `WetBlock`) imports the same labels
  and `humanize` from the editor through an alias.

Neither is complete against the schema or unambiguous, and the reading a
jurist signs off in one tool is not the reading another tool shows. Writing a
full reading is also easy to get subtly wrong: the obvious Dutch for several
operations gives two different trees the same text. The inventory below lists
those pitfalls next to what the editor does today.

### Inventory

The schema (`schema/v0.8.0/schema.json`, `definitions/operationType`) has 28
operations. Per operation, what the editor shows and what an obvious full
reading gets wrong:

| Operation | `operationTree.js` (label / subtitle) | Pitfall for a full reading |
|---|---|---|
| ADD | optellen / `a + b`, "som van n waarden" past 3 | `a plus b` is also the obvious reading of DATE_ADD |
| SUBTRACT | aftrekken / `a − b` | none |
| MULTIPLY | vermenigvuldigen / `a × b` | none |
| DIVIDE | delen / `a ÷ b` | none |
| MIN | minimum / `min(a, b)` | without a closing delimiter, `de kleinste van a en b plus c` has two parses |
| MAX | maximum / `max(a, b)` | `max(0, a−b)` and `max(a−b, 0)` both invite `het deel van a boven b`: two trees, one text |
| AND / OR | en / of, "n condities" past 3 | unaccented `en`/`of` collide with words inside names |
| NOT | niet / `niet x` | `niet x` is also the obvious reading of `EQUALS(x, false)` |
| EQUALS | gelijk aan / `x = y` | reading `EQUALS(x, true)` as `x` makes it the same text as a bare boolean `x`, which the engine treats differently when `x` is null |
| GREATER_THAN … LESS_THAN_OR_EQUAL | groter dan … / `>`, `≥` … | none |
| IF | als/dan / "als/dan operatie" | a nested IF in a `dan` branch needs a delimiter |
| IN | in lijst / `x in [a, b]` | none |
| LIST | lijst / `[a, b]` | none |
| FOREACH | voor elk / `voor elke x in c, optellen` | `voor elke … geldt` fits AND only; MIN, MAX, OR and no combine are not universal claims |
| AGE | leeftijd / `leeftijd a op b` | editor: operands that are operations are not traversed |
| DATE_ADD | datum optellen / `d + offset` | editor: hides the offset |
| DATE | datum / reads `node.value`, which DATE does not have | editor: always "(leeg)" |
| DAY_OF_WEEK | dag van de week / `dag van d` | none |
| DATE_DIFF | datumverschil / `a tot b in dagen` | `het aantal dagen tussen a en b` drops the sign (the result is signed, RFC-021) |
| DATE_PART | datumonderdeel / `jaar uit d` | none |
| START_OF | begin van / `begin van de maand van d` | none |
| ROUND | **no label** (`ROUND`) | a postfix `x, afgerond op n decimalen` leaves the scope of "afgerond" unclear |
| CEIL / FLOOR | **no label** | missing |

Further differences that are not per operation:

- The editor's `getChildOperations` does not descend into `subject`,
  `date_of_birth`, `reference_date`, `year`/`month`/`day` or
  `years`/`months`/`weeks`/`days`. An operation in any of those places is
  missing from the tree.
- The editor keeps labels for operations the schema no longer has (`SWITCH`,
  `NOT_EQUALS`, `NOT_NULL`, `NOT_IN`, `CONCAT`).
- `humanize` lowercases an all-caps name, so `PERCENTAGE_LID_5` and
  `percentage_lid_5` read the same.
- Money goes through `Intl.NumberFormat`, whose output depends on the ICU data
  of the runtime.
- For an operation it has no label for, the editor falls back to the code,
  silently.

## Decision

There is one reading of an action tree, **RegelRijm**, defined by the grammar
below and implemented once, in the frontend. It is not a language of its own:
it is generated from the YAML every time a rule is shown, so it cannot drift
from what the engine runs. Every tool that shows an action to a person
(editor, presenter, reports) uses it. The reading is for people who *read*;
it is not an input format. Modellers write YAML.

The requirements it meets:

1. **Complete.** Every value of `operationType` in the current schema has a
   form. A test reads the enum from the schema and fails on an operation
   without one. There is no fallback form.
2. **Unambiguous.** Two trees that differ after normalisation (below) never
   give the same text.
3. **Proven by a round trip.** A parser, test-only, satisfies
   `parse(render(t)) == normalise(t)` for every action in every corpus in the
   repository and for generated trees.
4. **Deterministic.** The same tree gives the same bytes, independent of map
   order, locale, time zone or runtime.
5. **Corpus-independent.** Without any glossary the reading is complete; a name
   without a term is humanised and marked.
6. **Literals follow the schema.** Dates, money in `eurocent` or `euro`,
   percentages, null, tables and FOREACH row references each have a fixed
   form.

### Normalisation

The round trip compares against `normalise(t)`, not `t`. Normalisation only
removes differences that carry no meaning for the reader *and* none for the
engine:

| Rule | Why it is allowed |
|---|---|
| An action's inline operation (`operation`, `values`, `value`, `precision` on the action) moves into `value` | The schema defines them as the same thing |
| Object keys in canonical order | YAML maps are unordered |
| `legal_basis` on an operation is dropped | It is provenance, shown by the UI next to the reading, not part of it |
| `FOREACH` without `as` gets `as: item` | Schema default |
| A YAML date object becomes its `YYYY-MM-DD` string | The engine reads both the same |
| An integer-valued float becomes an integer (`2.0` → `2`) | The engine's `Value` has no integer-valued decimal (`Int` vs `Decimal`) |
| Nested AND in AND, OR in OR, ADD in ADD, MULTIPLY in MULTIPLY are flattened, unless the inner one is empty | Associative under the engine's semantics, including Kleene logic for unknown (RFC-036). An empty inner ADD or MULTIPLY is an engine error and stays visible. Regrouping a decimal sum or product can differ past 28 significant digits, which no rule in the corpus comes near |

Not normalised, because the engine can tell the difference: operand order
(also of commutative operations), `EQUALS(x, true)` versus `x`, an IF nested in
a `default` versus extra cases (an unknown condition stops the chain, RFC-036),
SUBTRACT and DIVIDE nesting.

### Grammar

The reading is a token sequence. Whitespace between tokens carries no meaning:
the layout below may break and indent anywhere between tokens, and the parser
treats any run of whitespace as one separator. **Parentheses carry the
structure, indentation only shows it.**

```ebnf
rule        = name , "wordt:" , expr , [ legend ] ;
legend      = "waarbij:" , definition , { definition } ;     (* see Legend *)
definition  = letter , "=" , expr ;
letter      = "A" | "B" | … | "Z" | "AA" | "BB" | … ;

expr        = choice | logic ;
choice      = "als" , logic , "dan" , logic ,
              { "anders als" , logic , "dan" , logic } ,
              [ "anders" , logic ]
            | "geen geval" , [ "anders" , logic ] ;      (* IF without cases *)

logic       = operand , "én" , operand                     (* AND, n = 2 *)
            | operand , "óf" , operand                     (* OR,  n = 2 *)
            | "aan alle volgende voorwaarden is voldaan:" , items             (* AND, n >= 3 *)
            | "aan ten minste één van de volgende voorwaarden is voldaan:" , items  (* OR, n >= 3 *)
            | operand ;
items       = bullet , logic , bullet , logic , bullet , logic , { bullet , logic } ;
bullet      = "•" | "••" | … ;                               (* the same throughout one list *)
operand     = "niet" , closed                                 (* NOT *)
            | comparison | arith ;

comparison  = arith , cmp_op , arith
            | arith , "is niet" , arith                       (* NOT(EQUALS(a, b)) *)
            | arith , "ontbreekt"                             (* EQUALS(a, null) *)
            | arith , "is bekend"                             (* NOT(EQUALS(a, null)) *)
            | arith , "is een van" , "(" , [ list ] , ")"     (* IN with values *)
            | arith , "staat in" , closed ;                   (* IN with value *)
cmp_op      = "is" | "is meer dan" | "is minder dan"
            | "is ten minste" | "is ten hoogste" ;

arith       = closed , "plus" , closed , { "plus" , closed }
            | closed , "min" , closed , { "min" , closed }
            | closed , "maal" , closed , { "maal" , closed }
            | closed , "gedeeld door" , closed , { "gedeeld door" , closed }
            | offsets , "na" , closed                         (* DATE_ADD *)
            | aggregate                                       (* FOREACH ADD/MIN/MAX/none *)
            | closed ;

closed      = atom | letter | "(" , expr , ")" | function ;
list        = expr , { ";" , expr } ;

(* Every function form starts with a keyword and ends with a closed argument
   or a parenthesis, so it is closed itself. *)
function    = nary_word , "(" , [ list ] , ")"                       (* AND/OR/arithmetic, n < 2 *)
            | "de kleinste van" , "(" , list , ")"                   (* MIN *)
            | "de grootste van" , "(" , list , ")"                   (* MAX *)
            | "het deel van" , closed , "boven" , closed             (* MAX(0, SUBTRACT(a, b)) *)
            | "de lijst" , "(" , [ list ] , ")"                      (* LIST *)
            | quantor                                                (* FOREACH AND/OR *)
            | "het aantal volle jaren tussen" , closed , "en" , closed   (* AGE *)
            | "geen termijn na" , closed                             (* DATE_ADD without offsets *)
            | day , month_word , "van" , closed                      (* DATE, literal day and month *)
            | "de datum met jaar" , closed , "," , "maand" , closed , "en dag" , closed  (* DATE *)
            | "de weekdag van" , closed                              (* DAY_OF_WEEK *)
            | "het aantal" , diff_unit , "van" , closed , "tot" , closed  (* DATE_DIFF *)
            | "het verschil van" , closed , "tot" , closed , "in" , name  (* DATE_DIFF, `in` a $variable *)
            | ( "het jaartal" | "het maandnummer" | "het dagnummer" ) , "van" , closed  (* DATE_PART *)
            | ( "de eerste dag van het jaar waarin" | "de eerste dag van de maand waarin" ) ,
              closed , "valt"                                         (* START_OF *)
            | rounding , "op" , precision , "(" , expr , ")" ;       (* ROUND/CEIL/FLOOR *)

aggregate   = "de som van" , closed , over                           (* combine: ADD *)
            | "de kleinste waarde van" , closed , over               (* combine: MIN *)
            | "de grootste waarde van" , closed , over               (* combine: MAX *)
            | "de lijst van" , closed , over ;                       (* no combine *)
quantor     = "voor elke" , name , "in" , closed , [ filter ] , "geldt" , closed           (* AND *)
            | "voor ten minste één" , name , "in" , closed , [ filter ] , "geldt" , closed ; (* OR *)
over        = "over elke" , name , "in" , closed , [ filter ] ;
filter      = "waarvoor" , closed ;

offsets     = offset , { "," , offset } , [ "en" , offset ] ;       (* years, months, weeks, days, in that order *)
offset      = closed , ( "jaar" | "jaren" | "maand" | "maanden" | "week" | "weken" | "dag" | "dagen" ) ;
diff_unit   = "dagen" | "maanden" | "jaren" ;
rounding    = "afgerond" | "naar boven afgerond" | "naar beneden afgerond" ;
precision   = "hele eenheden" | "1 decimaal" | digits , "decimalen"
            | "veelvouden van" , power_of_ten                        (* negative precision *)
            | "hele euro's" | "hele centen" ;                        (* by the unit of the operand *)
nary_word   = "én" | "óf" | "plus" | "min" | "maal" | "gedeeld door" ;

atom        = name | literal ;
name        = term | untranslated | name , "van" , name ;            (* $a.b reads "b van a" *)
term        = "‹" , text , "›" ;
untranslated= "[" , text , "]" ;
literal     = "waar" | "onwaar" | "geen" | number | money | percent | quantity
            | date_literal | string ;
string      = "“" , text , "”" ;
```

Keywords are matched longest first (`geen geval` before `geen`, `is ten
minste` before `is`). The small words `en`, `na`, `tot`, `van`, `in`, `op` and
`boven` only appear inside one fixed production each; no production puts `van`
directly after an operand except `name "van" name`, so a `van` after a name
always continues the name path.


### Scope and parentheses (requirement 2)

These are the choices that make the grammar unambiguous. Each lists the
alternative that was not taken.

1. **`én` and `óf` have no precedence over each other.** A mix is always
   parenthesised: `a én ( b óf c )`. Legal Dutch "a en b of c" is ambiguous
   and readers know it; the reading never relies on a convention they would
   have to be taught.
   *Alternative:* `én` binds tighter, as in most programming languages. Fewer
   parentheses, but a reader who does not know the rule reads it wrong.
2. **`niet` takes one closed operand and is not itself closed.** `niet [x]`,
   `niet ( [a] is meer dan [b] )`. A NOT inside a comparison, a sum or a
   function argument is parenthesised: `[a] is ( niet [b] )`. That keeps
   `[a] is niet [b]` free for exactly one tree, `NOT(EQUALS(a, b))`, and
   `niet [a] is 5` cannot occur.
   *Alternative:* always `niet ( … )`, also around a single name. Uniform, but
   it adds a parenthesis pair to every negated name.
3. **Comparison binds weaker than arithmetic, stronger than `niet`/`én`/`óf`.**
   `[a] plus [b] is meer dan [c]` needs no parentheses; `[a] is [b] én [c] is
   [d]` neither. Comparisons do not chain: `( [a] is [b] ) is waar`.
   *Alternative:* parenthesise arithmetic inside a comparison too.
4. **Arithmetic operators have no precedence over each other.** `[a] plus (
   [b] maal [c] )`. Different operators never share a level without
   parentheses, and SUBTRACT and DIVIDE are n-ary left-to-right as in the
   engine: `[a] min [b] min [c]` is one SUBTRACT with three operands, while
   `[a] min ( [b] min [c] )` is a nested one.
   *Alternative:* `maal`/`gedeeld door` before `plus`/`min`. Familiar from
   school, but the reading would then have two forms for one tree depending on
   whether the redundant parentheses are kept.
5. **A nested IF is always parenthesised**, also as a whole `dan` or
   `anders` branch: `als [a] dan ( als [b] dan 1 anders 2 ) anders 3`. Only
   the IF that is the whole rule goes without. This removes the dangling
   `anders`.
   *Alternative:* indentation decides. That makes layout meaningful, and a
   copy into an e-mail destroys the meaning.
6. **Every argument of a function form is closed** (a name, a literal, a
   function form, or parenthesised), and every function form starts with a
   keyword. A function form therefore ends where its last argument ends:
   `het aantal volle jaren tussen [a] en [b] plus 1` is `AGE(a, b) + 1`, and
   `AGE(a, b + 1)` reads `… en ( [b] plus 1 )`. DATE_ADD is the exception that
   proves the rule: it starts with its offsets (`3 dagen na [d]`), so it is not
   closed and sits at the level of arithmetic. It needs no parentheses as a
   comparison operand (`[x] is ten minste 3 dagen na [d]`) and gets them as a
   function argument, which keeps the `en` of `1 maand en 3 dagen` apart from
   the `en` of AGE. Rounding takes its operand in parentheses always.
7. **Forms that would collide get different words.** DATE_ADD reads
   `3 dagen na [d]`, not `[d] plus 3 dagen`, because ADD of a value in days
   reads `[d] plus 3 dagen`. A literal date reads `1 januari 2025`, the DATE
   operation `1 januari van 2025`.
8. **Sugar is one-way and exact.** `is niet`, `ontbreekt`, `is bekend`
   and `het deel van a boven b` each stand for exactly one tree shape, and
   that shape never renders in the general form. `het deel van … boven …` is
   `MAX` with exactly the operands `0` and a two-operand `SUBTRACT`, in that
   order; `MAX(SUBTRACT(a, b), 0)` reads `de grootste van ( … ; 0 )`.
9. **Degenerate arities have their own form.** AND, OR and the arithmetic
   operations with fewer than two operands read `én ( [a] )`, `plus ( )`,
   so that `AND([a])` does not read as `[a]`. An AND or OR of three or more
   conditions always reads as an enumeration (below), so the infix form
   `[a] én [b]` is for exactly two.
10. **No normalisation of `EQUALS(x, true)` to `x`.** `[x] is waar` and `[x]`
    are different trees: `EQUALS` is false on a non-boolean or null `x`, while
    a bare `x` in a condition is not.
11. **A form that can end in an optional part is not closed.** A FOREACH that
    sums, takes an extreme or collects (`de som van B over elke [x] in C
    waarvoor F`) may end in `waarvoor F`, so as the collection of another
    FOREACH that `waarvoor` could belong to either. Such a form sits at the
    level of arithmetic and is parenthesised as a function argument. The
    generated-tree test found this one; it is the same dangling-suffix
    problem as the dangling `anders`. The quantors (`voor elke … geldt B`)
    end in a closed operand and stay closed.
12. **A DATE_DIFF unit that is a variable comes last.** `het verschil van [a]
    tot [b] in [eenheid]`, not `het aantal [eenheid] van …`: a name followed
    by `van` continues the name path, so the unit cannot stand in front.

### Names and terms (requirement 5)

A reference `$naam` reads as:

1. its **term** if one is known: `‹de peildatum›`;
2. otherwise its **humanised name**: `[hoogte zorgtoeslag]`.

Humanising replaces `_` with a space and nothing else: case is kept, so it is
reversible (`[PERCENTAGE LID 5]` and `[percentage lid 5]` are different
names). Square brackets look like what they are, a placeholder waiting for a
word, and a counter finds them without knowing the vocabulary.

A dotted reference `$medebewoner.inkomen` reads `[inkomen] van [medebewoner]`,
deepest segment first.

Terms come from, in order:

- a small built-in list for engine context variables (`$referencedate` →
  `‹de peildatum›`); this list is generic and lives with the implementation;
- an optional `term` field on an input, output, parameter or structured
  definition (schema change, part of this RFC, separate from the reading);
- an optional glossary passed in by the caller, so a corpus kept elsewhere
  can keep its words out of this repository.

A glossary is checked when loaded: terms are unique, non-empty and contain no
`‹`, `›`, `[`, `]`, `“` or `”`. Because every name is delimited, injectivity
does not depend on what the terms say; a term may contain `is`, `en` or `van`.

### Literals (requirement 6)

| Value | Reading | Notes |
|---|---|---|
| `true` / `false` | `waar` / `onwaar` | |
| `null` | `geen` | RFC-036 absence; `EQUALS(x, null)` reads `[x] ontbreekt`, its negation `[x] is bekend` |
| string | `“HUWELIJK”` | verbatim; `”` and `\` inside are escaped with `\` |
| string `YYYY-MM-DD` that is a valid date | `1 januari 2025` | anything else stays a string |
| number, no unit | `1500`, `0,5`, `-3` | decimal comma, no thousands separator, never an exponent, shortest exact digits |
| number, unit `eurocent` | `€ 1.500,00` | value / 100, at least two decimals, more if the value has them |
| number, unit `euro` | `€ 15,00` | same format |
| number, unit `percentage` | `21%`, `21,5%` | |
| number, unit `ratio` | `0,21` | plain number |
| number, unit `years`/`months`/`weeks`/`days` | `1 jaar`, `5 jaren`, `1 dag`, `3 dagen` | |

A literal has no unit of its own. Its unit is inferred from its position, the
same way during rendering and parsing, so the round trip is exact:

- the unit of an *expression* is the declared unit of a reference, or for
  ADD, SUBTRACT, MIN, MAX and IF the unit of its first operand (branch) that
  has one, or for ROUND, CEIL and FLOOR the unit of its operand; otherwise it
  has none;
- the root takes the unit of the action's output;
- a comparison operand takes the unit of the other side's expression;
- an operand of ADD, SUBTRACT, MIN or MAX, a branch of IF and an item of LIST
  take the unit of the first sibling expression that has one, else the unit
  of their parent;
- an item of an inline IN list takes the unit of the subject's expression, with
  no fallback to the parent;
- the operand of ROUND, CEIL and FLOOR, and the body of a FOREACH that sums,
  takes an extreme or collects, take the unit of their parent;
- operands of MULTIPLY and DIVIDE, logic, conditions, FOREACH collections and
  filters, DATE_ADD offsets and all date-operation arguments have no unit.

Declared units come from `type_spec.unit` on inputs, outputs and parameters,
and on structured definitions.

**Tables.** A row reference inside FOREACH is a dotted name (`[bijdrage] van
[medebewoner]`). The reading of a definition whose value is a table is not
part of the action reading and is not specified yet.

### Forms, with an example each

| Operation | Example YAML | Reading |
|---|---|---|
| ADD | `values: [$a, $b]` | `[a] plus [b]` |
| SUBTRACT | `values: [$a, $b, 10]` | `[a] min [b] min 10` |
| MULTIPLY | `values: [$a, 0.5]` | `[a] maal 0,5` |
| DIVIDE | `values: [$a, 12]` | `[a] gedeeld door 12` |
| MIN | `values: [$a, $b]` | `de kleinste van ( [a]; [b] )` |
| MAX | `values: [$a, $b]` | `de grootste van ( [a]; [b] )` |
| MAX (sugar) | `values: [0, {SUBTRACT: [$a, $b]}]` | `het deel van [a] boven [b]` |
| AND | `conditions: [$a, {EQUALS: [$b, 1]}]` | `[a] én [b] is 1` |
| AND (3 or more) | `conditions: [$a, $b, $c]` | `aan alle volgende voorwaarden is voldaan: • [a] • [b] • [c]` |
| OR | `conditions: [$a, $b]` | `[a] óf [b]` |
| OR (3 or more) | `conditions: [$a, $b, $c]` | `aan ten minste één van de volgende voorwaarden is voldaan: • [a] • [b] • [c]` |
| NOT | `value: $a` | `niet [a]` |
| NOT (EQUALS) | `value: {EQUALS: [$a, 3]}` | `[a] is niet 3` |
| EQUALS | `subject: $a, value: "X"` | `[a] is “X”` |
| EQUALS (null) | `subject: $a, value: null` | `[a] ontbreekt` |
| NOT (EQUALS null) | `value: {EQUALS: [$a, null]}` | `[a] is bekend` |
| GREATER_THAN | `subject: $a, value: 5` | `[a] is meer dan 5` |
| LESS_THAN | `subject: $a, value: 5` | `[a] is minder dan 5` |
| GREATER_THAN_OR_EQUAL | `subject: $leeftijd, value: 18` | `[leeftijd] is ten minste 18` |
| LESS_THAN_OR_EQUAL | `subject: $a, value: 5` | `[a] is ten hoogste 5` |
| IF | `cases: [{when: $a, then: 1}], default: 0` | `als [a] dan 1 anders 0` |
| IN (values) | `subject: $a, values: [1, 2]` | `[a] is een van ( 1; 2 )` |
| IN (value) | `subject: $a, value: $lijst` | `[a] staat in [lijst]` |
| LIST | `items: [$a, $b]` | `de lijst ( [a]; [b] )` |
| FOREACH ADD | `collection: $m, as: x, filter: …, body: $x.b, combine: ADD` | `de som van [b] van [x] over elke [x] in [m] waarvoor ( [leeftijd] van [x] is ten minste 21 )` |
| FOREACH AND | `combine: AND` | `voor elke [x] in [m] geldt ( … )` |
| FOREACH OR | `combine: OR` | `voor ten minste één [x] in [m] geldt ( … )` |
| FOREACH MIN / MAX | `combine: MIN` | `de kleinste waarde van ( … ) over elke [x] in [m]` |
| FOREACH (no combine) | `collection: $m, as: x, body: …` | `de lijst van ( … ) over elke [x] in [m]` |
| AGE | `date_of_birth: $g, reference_date: $p` | `het aantal volle jaren tussen [g] en [p]` |
| DATE_ADD | `date: $d, months: 1, days: 3` | `1 maand en 3 dagen na [d]` |
| DATE | `year: $j, month: 1, day: 1` | `1 januari van [j]` |
| DATE (general) | `year: $j, month: $m, day: 1` | `de datum met jaar [j], maand [m] en dag 1` |
| DAY_OF_WEEK | `date: $d` | `de weekdag van [d]` (0 = maandag) |
| DATE_DIFF | `from: $a, to: $b, in: days` | `het aantal dagen van [a] tot [b]` |
| DATE_PART | `date: $d, in: year` | `het jaartal van [d]` |
| START_OF | `date: $d, in: month` | `de eerste dag van de maand waarin [d] valt` |
| ROUND | `value: {DIVIDE: [$a, 12]}, precision: 0` | `afgerond op hele eenheden ( [a] gedeeld door 12 )` |
| CEIL | `value: $a, precision: 2` | `naar boven afgerond op 2 decimalen ( [a] )` |
| FLOOR | `value: $a, precision: -2` | `naar beneden afgerond op veelvouden van 100 ( [a] )` |
| ROUND (money) | `value: $bedrag_euro, precision: 0` | `afgerond op hele euro's ( [bedrag euro] )` |
| ROUND (cents) | `value: $bedrag_cent, precision: -2` | `afgerond op hele euro's ( [bedrag cent] )`; precision `0` reads `hele centen` |

A rule as a whole: `[recht op zorgtoeslag] wordt: [a] én [b] is ten minste 18`.

### Enumerations

An AND or OR of three or more conditions reads the way RegelSpraak, the
controlled rule language of the Belastingdienst, lists conditions: a head,
then one bulleted item per line. The bullet shows how deep the list is: `•`
for a list, `••` for a list inside one of its items, and so on.

```
als aan ten minste één van de volgende voorwaarden is voldaan:
	• [a]
	• [b] én [c] is niet waar
	• aan alle volgende voorwaarden is voldaan:
		•• [d]
		•• [e]
		•• niet [f]
dan …
```

Three choices keep this unambiguous and short:

1. **The form follows the number of conditions only**, never the width, so
   the token sequence stays independent of the layout.
2. **The bullets delimit the items.** Every item of one list carries the same
   bullet, and a list inside an item carries a longer one. An item therefore
   ends at the next bullet of its own list, and may itself be an `én` or `óf`
   without parentheses; a list inside an item needs none either. Only a choice
   (IF) inside an item keeps its parentheses, by the rule for nested IFs.
3. **No closing word.** The enumeration sits at the level of `én`/`óf`, so it
   is parenthesised wherever such an operand would be and is followed only by
   what may follow one (`dan`, `anders`, `;`, `)`, the next bullet, the end).
   Whether all or one of the items must hold is said once, in the head.

*Alternative:* the enumeration of the Aanwijzingen voor de regelgeving,
`a. …; b. …; en c. …`. Familiar from the text of a law and citable as
"onderdeel c", but the closing `en`/`of` repeats the head, and an item that is
itself an `én`, or a list inside an item, then needs parentheses to show
where the item ends.

*Not taken from RegelSpraak:* its synonyms for one assignment (the reading
keeps `wordt:`), quantifiers RegelRijm has no operation for (`ten minste n`,
`precies n`), and treating an empty value as 0 in a sum, which the engine does
not do (RFC-036).

### Legend

A long part that occurs more than once in a rule reads once, in a legend
under the rule, the way a formula in a law is followed by `waarbij:`:

```
[hoogte zorgtoeslag] wordt:
	het deel van ( als [heeft toeslagpartner] is waar dan 2 maal [standaardpremie] anders [standaardpremie] )
		boven ( ( ( als … ) maal de kleinste van ( [in aanmerking genomen toetsingsinkomen]; A ) )
			plus ( als [in aanmerking genomen toetsingsinkomen] is meer dan A dan … anders € 0,00 ) )
waarbij:
	A = als [heeft toeslagpartner] is waar dan [drempelinkomen aanvrager met toeslagpartner] anders [drempelinkomen alleenstaande]
```

Which parts get a letter is a function of the tree, so the reading stays
deterministic:

1. Read the rule in place and take, for every operation, its reading on one
   line (with the units of its position, so `€ 15,00` in a euro and in a
   eurocent position count as the same text).
2. A candidate is a text of at least 40 code points that occurs at least twice.
3. Take candidates longest first. A candidate is taken when it still occurs at
   least twice outside the occurrences of parts already taken; inside the one
   occurrence that is read as a definition it still counts.
4. Letters go in order of first use: the rule first, then each definition in
   turn, which may name later letters but never earlier ones or itself.

Expanding every letter into its definition gives back exactly the reading
without a legend, so the legend does not touch injectivity: two trees with the
same legend reading have the same expanded reading. A letter is closed, the
same as a parenthesised expression; the test parser substitutes the parsed
definition for the letter and only then infers the units of the literals in
it. Numbers in the editor pane follow the reading without a legend, so a
part keeps its number whether a letter stands for it or not. The pane itself
folds by depth and shows no legend.

*Alternative:* letters for every deep part, as a formula in a law sometimes
does. That turns every rule into a crossword; folding by depth already
serves that, and the legend is kept for what repeats.

### Layout

Layout is presentation and does not change the token sequence. A construct
that fits in 160 code points stays on one line; otherwise each operand goes on
its own line, indented one tab, with the connective (`én`, `plus`, `anders
als`) at the start of the line. An opening parenthesis stays on the line of
what it opens and the inside breaks one level deeper, so no line consists of
only a parenthesis; the closing one ends the last line of the block. An
enumeration and a legend always break, one item or letter per line. Width is
counted in Unicode code points, never in bytes, with an indentation tab
counted as four.

### Implementation

One implementation renders a tree into a **token stream** (`keyword`,
`term`, `name`, `literal`, `letter`, `fold`, `hole`, `error`, each with its path in the
tree and, for a name, its reference); the text is the concatenation of the
tokens with the layout applied. The editor and presenter render the token
stream as HTML (a term is a styled span without its `‹ ›`, an untranslated
name is visibly marked); plain text is used for tests, diffs and reports.

**Location: `packages/frontend-shared/src/regelrijm/`**, a set of pure
JavaScript modules without Vue or browser dependencies, imported as
`@regelrecht/frontend-shared/regelrijm/index.js`. It is part of the
frontend, not a language with its own toolchain:

- Determinism: no `Intl`, no locale, no `Date.now`. Money moves its decimal
  point on the digit string, never by float division.
- Works on the raw tree, not a typed model, so a half-edited tree in the
  editor still renders, with an explicit hole token for a missing field
  (`⟨ontbreekt: value⟩`) and an error token for an unknown operation.
- The editor and the presenter import the same module; a report or a
  pipeline step runs it under Node (`scripts/regelrijm-report.mjs`).

`renderAction(action, { article, glossary })` gives the full reading;
`renderFocus(action, path, { depth })` the reading of one operation with
deeper operations folded (see "The editor pane").

The parser lives in `test-support/parse.js`. It returns *every* parse of a
text, it is not exported from the package index, and nothing outside the
tests imports it.

### The editor pane

The editor shows RegelRijm as a pane view, "RegelRijm", next to Tekst,
Machine and the others. Like every pane it has a `panel.*` feature flag,
`panel.regelrijm`, which is off by default. No other pane changes.

- **Every rule** of the selected article is read as it is being edited, so a
  change in the Machine pane or the YAML shows at once. A tree half-way
  through an edit reads with holes, not with an error.
- **Depth.** A rule reads to a chosen depth (1, 2, 3 or everything; default
  2). An operation deeper than that is folded into its **signature** (below):
  `[hoogte zorgtoeslag] wordt: het deel van ⟨bedrag uit [heeft
  toeslagpartner] en [standaardpremie]⟩ boven ⟨bedrag uit [heeft
  toeslagpartner] en [in aanmerking genomen toetsingsinkomen]⟩`.
- **Opening a fold.** Clicking a fold opens it in place one level deeper: the
  part reads in full and its own parts are folded in turn, so a reader goes
  down layer by layer without leaving the rule. Which parts are open is view
  state only; another article or depth starts folded again. Numbers follow
  reading order and are the same at every depth.
- **Following a name.** A name that a rule computes, in this article,
  another article or another regelwerk (`source.regulation`), can be clicked
  and leads to that rule. Parameters, definitions, engine context and
  FOREACH variables are not links.
- **Editing stays where it is.** "Actie openen" opens the action sheet the
  Machine pane uses.

A folded text is a view; the reading that is tested and signed off is the
unfolded one.

#### Signatures

A folded part says *what* it gives and *what it reads*, not *how* it computes
it, the way an editor shows the signature of a function call rather than its
body: `⟨bedrag uit [inkomen] en [percentage inkomen]⟩`,
`⟨voorwaarde over [x] en [y]⟩`. Both halves are derived from the tree and the
article, never written by anyone:

- **The kind** comes from the operation (a comparison, `én` or `óf` is a
  `voorwaarde`; `DATE_ADD` a `datum`; `DATE_DIFF` in days an `aantal dagen`)
  or, for arithmetic and choices, from the unit of the part's position, the
  same unit the literals in that position get (`bedrag`, `percentage`,
  `verhouding`, `aantal jaren`, …). Without a unit it is `getal` or `waarde`.
- **The inputs** are the free references of the part in reading order, each
  once. A name the part binds itself (the `as` of a FOREACH inside it) is not
  an input, and neither is a constant of the article (a name under
  `definitions`): constants are part of how the part computes, not of what it
  depends on. At most three are named, the rest counted (`en nog 2`); opening
  the fold shows the rest. Without inputs it reads
  `uit vaste waarden`.

A part whose full reading is no longer than its signature is not folded,
because there folding would cost reading instead of saving it. Two parts can
have the same signature; their numbers keep them apart. Signatures are a view
like the rest of this section and are not parsed.

*Alternative:* the operation and number (`⟨1.2 product⟩`), as before. That
says how a part is computed and nothing about what it means, so a reader had to
open every fold to learn anything.

### Tests

- **Schema coverage**: read `definitions/operationType` from the latest
  schema; every value renders with a form that is not a fallback.
- **Round trip** over `corpus/regulation`: for every action,
  `parse(render(t)) == normalise(t)`.
- **Generated trees** (seeded, `test-support/generate.js`): random trees over
  all 28 operations, with awkward names (`van`, `_lead`, upper and lower
  case), terms that contain keywords, strings with quotes and delimiters,
  invalid dates and every unit; round trip with exactly one parse, and
  injectivity (`render(a) == render(b)` implies `normalise(a) == normalise(b)`).
- **Determinism**: rendering the same tree twice, and with shuffled map keys,
  gives the same bytes.
- **Report per corpus**: number of actions, number of untranslated names
  (distinct and occurrences), longest line, actions that do not fit on one
  line.

## Why

### Benefits

- A jurist reads the same text in the editor, in a presentation and in a
  generated report, and a sign-off on that text refers to one thing.
- Ambiguity is tested, not argued: the round trip fails the day a new form
  makes two trees read the same.
- A new operation in the schema fails the build until it has a form.
- A corpus kept elsewhere gets the full reading with its own glossary,
  without its words entering this repository.

### Tradeoffs

- Explicit parentheses (`én` vs `óf`, mixed arithmetic, rounding) make some rules
  longer than the legal sentence they model.
- Delimiters around every name (`‹ ›`, `[ ]`) are noise in plain text; they
  disappear only in the HTML rendering.
- `[x] is waar` is longer than `x`, so rules that compare booleans with
  `true` read heavier than a looser reading would.
- A glossary that gives two names the same term loses one of them: the
  reading refuses it rather than read two different values alike.
- Unit inference needs the article's declarations, so a fragment rendered
  without its article loses its money format.

### Alternatives Considered

**Alternative 1: Keep `operationTree.js` and extend it.**
- Add the missing labels and descend into all operands.
- Rejected: it is a summary by design ("5 condities"), it descends into only
  part of the tree, and its number format depends on the runtime.

**Alternative 2: Terms without delimiters.**
- `de peildatum` instead of `‹de peildatum›`.
- Rejected for the canonical text: injectivity would depend on every term
  avoiding every keyword (`is`, `en`, `van`, `in`, `na`, `tot`, …), which a
  glossary written by jurists will not do. The HTML rendering shows terms
  without delimiters anyway.

**Alternative 3: A Rust crate, exposed to the browser through the engine's WASM build.**
- One implementation for pipeline and frontends, completeness by an
  exhaustive `match`.
- Not chosen: the reading belongs to the frontend, where people read rules;
  it should render synchronously, also for a half-edited tree, without
  waiting for the engine to load. A pipeline step that needs the text runs
  the same module under Node.

**Alternative 4: A writable notation.**
- Let modellers write the Dutch and generate the YAML.
- Rejected: it is a second source language with its own error messages and
  edge cases. Jurists read, modellers write YAML.

### Implementation Notes

- Line width 160 and tab indentation, so most rules fit one line of a wide
  pane and a nested part is indented by one tab per level.
- `OPERATION_LABELS`, `describeSubtitle` and `derivedTitle` in the editor's
  operation tree are not yet replaced; that is the next step, together with
  the presenter's `WetBlock`.
- The reading covers the operations of the latest schema. Every schema from
  v0.5.0 on uses a subset of them, so those rulework versions read in full.
  Older versions had operations that were removed since (`SWITCH`,
  `NOT_EQUALS`, `NOT_IN`, `NOT_NULL`, `CONCAT`, `SUBTRACT_DATE`); they read as
  an error token, not as something else.
- The optional `term` field is a schema change and gets its own schema
  version; the reading works without it.
- `formatValue`, `formatOutputValue` and the euro formatting of *results* in
  `outputFormat.js` are about engine output values, not about the tree, and
  stay where they are.
