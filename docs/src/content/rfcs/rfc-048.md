## Context

An article asks for parameters. Who supplies each one was only written as prose in its `description`, such as "Herkomst: de aanvrager zelf, in de aanvraag". The engine does not need this. A runtime that carries out a procedure does. It cannot read prose, so the same knowledge ended up in configuration a second time: which parameters form the application form, which period an application asks for, which ones a register supplies, and which ones the official judges.

The law already divides this work, as the table in §1 shows. Classifying a parameter is interpretation, and whoever writes the prose already does it.

## Decision

### 1. `origin` on a parameter

A parameter can carry an `origin`: a fixed value, plus a `grondslag` that says who supplies it.

```yaml
parameters:
  - name: naam_aanvrager
    type: string
    origin:
      waarde: BELANGHEBBENDE
      grondslag: algemene_wet_bestuursrecht#4:2 lid 1
  - name: inkomensgegeven
    type: amount
    origin:
      waarde: REGISTER
      register: algemene_wet_inzake_rijksbelastingen
      grondslag: algemene_wet_inzake_rijksbelastingen#21e lid 1
```

The `grondslag` is given only when the provision's text says it. Awb 4:2 lid 1 says the application contains "de naam en het adres van de aanvrager". A basis that needs several provisions read together is no `grondslag`. Then the origin has none, and a comment explains the reasoning, marked as an assumption or own choice. Example: no article says the applicant gives the BSN on an Awir application.

| `waarde` | Meaning | Typical `grondslag` |
|---|---|---|
| `BELANGHEBBENDE` | what the applicant supplies or chooses: the content of the application, the decision requested, the period | Awb 4:2 lid 1 and 2; "de aanvraag bevat …" in the special law |
| `DOSSIER` | a fact from the course of the case at the administrative body | Awb 4:5, 4:15, 3:41; the article of the act itself |
| `OORDEEL` | a judgement the administrative body gives when it decides | Awb 3:2, 3:4, 3:46 |
| `REGISTER` (with `register: <regulation>`) | a fact from a register kept by or under that regulation | the provision that lets the consumer ask |
| `KANAAL` | what the intake channel says: who logs in and on whose behalf | Awb chapter 2, section 2.3; the implementing policy for the channel |

Values are Dutch and upper case, like `legal_character`. The `grondslag` reads `<regulation>#<article>`, optionally with ` lid <n>`. `origin` is optional. A parameter that a calling law passes in, which covers most of the Awb, needs none.

`REGISTER` means the value comes through a `source` to the keeper's implementing policy ([RFC-045](/rfcs/rfc-045) §1). `register` names the law that sets up the register. It is a value of its own because a runtime must know the fact exists before the application, and a `source` does not say that. `register` is required with `REGISTER` and forbidden with any other value.

### 2. Roles

A `rol` tells the runtime what the parameter is within the decision.

| `rol` | With | Meaning |
|---|---|---|
| `TIJDVAK` | `BELANGHEBBENDE` | the period the decision covers, chosen by the applicant as part of the request (Awb 4:2 lid 1) |
| `GEVRAAGD_BESLUIT` | `BELANGHEBBENDE` | the decision requested (Awb 4:2 lid 1 onder c); the runtime fills it if one decision is taken on the application, otherwise the applicant chooses |
| `BESLUIT` | `DOSSIER` | the decision already taken that the parameter is about; the runtime gives its id ([RFC-047](/rfcs/rfc-047)) |

The period is `BELANGHEBBENDE`, because the applicant chooses it. An earlier draft marked it by the `grondslag` Awb 4:2 lid 1, which gave one provision two meanings. Now it has its own role:

```yaml
- name: aangevraagd_berekeningsjaar
  type: number
  origin:
    waarde: BELANGHEBBENDE
    grondslag: algemene_wet_inkomensafhankelijke_regelingen#15 lid 1
    rol: TIJDVAK
```

Which law version a period's decision applies is in [RFC-050](/rfcs/rfc-050) §4.

### 3. Implementing policy can override

The law gives the default. An article with layer `UITVOERINGSBELEID` may override it, again with a `grondslag`:

```yaml
machine_readable:
  origins:        # the body retrieves this itself, rather than asking for it
    - regulation: een_bijzondere_wet
      parameter: verdeeltabel
      origin: {waarde: REGISTER, register: een_registerwet, grondslag: een_beleid#4 lid 1}
```

A process uses the override from loaded policy whose `competent_authority` is the authority it acts for. Otherwise it uses the law. Under a mandate (Awb 10:1) the process does not take over the mandating authority's overrides. Two policies of one actor that disagree on a parameter are a load-time error. An override only classifies. When it sets `REGISTER`, its `grondslag` names the article of the same policy that holds the `source`.

### 4. What a process runtime does with it

The engine ignores `origin` and `origins`. A process runtime uses them:

- **Application fields.** A parameter of the application with `BELANGHEBBENDE` or `KANAAL` is a field of the recorded application ([RFC-046](/rfcs/rfc-046) §3, [RFC-049](/rfcs/rfc-049)).
- **The period.** The `rol: TIJDVAK` parameter gives the period of the decision.
- **The decision requested.** The runtime fills the `rol: GEVRAAGD_BESLUIT` parameter if one decision is taken on the application. If more are, the applicant chooses one of them.
- **A wrong source is an error.** A value from a supplier that does not fit the origin stops the runtime. That holds with `required: false` too, and when a fitting supplier also exists.
- **Completeness at start-up.** Every parameter the caller must supply needs a fitting supplier. A missing one is a start-up error that names the parameter, the origin and the `grondslag`.
- **The offer.** A portal offer may only read `KANAAL`, `REGISTER`, or `BELANGHEBBENDE` with `rol: TIJDVAK`. Nothing else is known before the application.
- **The decision form.** The official fills in the `OORDEEL` parameters, grouped per article of their `grondslag`.
- **`required` stays engine semantics.** The runtime does not derive it from `origin`. A fact that does not apply is `nullable` and passed as `null`.

## Why

### Benefits

- Knowledge once repeated in configuration now follows from the law, with a provision a legal expert can check (RFC-027).
- A process missing a supplier fails at start-up, naming the provision. It does not wait for the first case to report "missing X".
- The application form follows from the law. Change who supplies a parameter and the form changes.

### Tradeoffs

- Classification is interpretation and can be wrong. The `grondslag` makes it checkable.
- `origins` in policy is a second place to look. It is limited to the actor's own policy, and conflicts are errors.
- Existing corpora carry prose. Converting it is a mapping per phrasing, and unclear phrasings stay without `origin`.
- `TIJDVAK` only goes with `BELANGHEBBENDE`, so a decision nobody applies for (an aanslag) cannot name its period this way. See [RFC-050](/rfcs/rfc-050) §5.

### Alternatives Considered

**Keep the prose and parse it.** Rejected: the prose varies per law and author, and the parser would be a hidden vocabulary.

**Name the supplying cell in the law.** Rejected: it ties a law to one deployment. The register binding says which system keeps a register (RFC-045 §1).

**Derive `required` from `origin`.** Rejected: `required` governs a missing value (RFC-036), and a law may require an applicant fact.

**A separate value for the period (`KADER`).** Rejected: the period is part of what the applicant asks for.

## Implementation in this pull request

- `packages/law-model` reads `origin` and `origins`. An unreadable entry is kept as written (`Declared::Invalid`), so a bad `origin` never stops a law from loading. A runtime that reads it reports the file and parameter. Older engines ignore unknown fields.
- Schema v0.8.0 declares `origin`: `waarde`, optional `grondslag`, optional `register` (required with `REGISTER`, forbidden otherwise) and optional `rol` (`TIJDVAK` and `GEVRAAGD_BESLUIT` only with `BELANGHEBBENDE`, `BESLUIT` only with `DOSSIER`). It does not declare `origins`, so a law using `origins` fails v0.8.0 validation until a later version.
- The corpus carries `origin` on Awir 15, the Awb 4:2 hook, the Awir procedure decisions and the fictitious policies. `packages/cel` uses it for application fields, the period and the decision requested.
- Not built here: the completeness check, the offer rule and the decision form. The proof of concept on branch `poc/chronolex` built them. They come with a runtime that has forms and a portal.
